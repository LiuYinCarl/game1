# Kenney 素材相关坑

## 隔行扫描 PNG：Godot 解码异常（"敌人变成方块"事件）

**现象**：给重甲武士配了 `towerDefense_tile266.png`，游戏里它渲染成一整块米色方块；用 sips/访达看同一张文件却是正常的图案。

**原因**：这批 Kenney Tower Defense Top-Down 素材的 PNG 是 **Adam7 隔行扫描**格式，其中 `tile266` 还是 `colortype=2`（RGB 无透明通道）。Godot 的 PNG 解码器对这种组合处理有问题，解码出错误的像素（整图米色噪声）。而 macOS 自带的 ImageIO（sips、访达、预览）能正确解码——所以**用系统工具预览永远看不出问题**，极具迷惑性。

**排查过程**（值得记下来）：
1. 先怀疑导入缓存坏了，删 `.import` 和 `.godot/imported` 重导——无效。
2. 用 Godot 脚本 `Image.load_from_file()` 直接解码文件，发现"文件本身就解码成米色满幅图"。
3. 写了个正确的 Adam7 解码器（7 个 pass 逐 pass 反滤波再散列像素）重写文件，解码结果稳定不变——证明**不是解码器 bug，文件内容按规范解出来就是这样**。
4. 回头核对素材，发现 tile266 本来就是一张米色圆盘地形砖——是当初挑图时把缩略图序号看串了，贴图配错了。隔行格式只是让"编辑器里看是 A、游戏里渲染成 B"更诡异。

**修复**：
- 用 Python（Adam7 逐 pass 解码）把项目里所有 Kenney 贴图重写成**标准非隔行 RGBA PNG**；
- 贴图重新对号入座：重甲武士 = tile268（绿色坦克）、掠夺者装甲车 = tile269（米色装甲车）。

**教训**：从素材包拷贴图时，先确认 Godot 里 `Image` 解码的 `used_rect` 和中心像素颜色是否合理（`Image.get_used_rect()` 撑满整画幅 + 单一颜色 = 大概率解码失败）；必要时统一转码成非隔行 RGBA。

## 受击闪白不要用过强 HDR 颜色

**现象**：兵营士兵近战时，目标看起来是"一堆白色方块"。

**原因**：受击闪白用 `Color(4, 4, 4)` 这类超亮 HDR 色，乘到贴图上所有像素都被饱和成纯白，小贴图的轮廓完全丢失；再加上多个士兵攻击冷却全部从 0 开始，每秒同步闪一次，观感就是整齐的方块闪烁。

**修复**：闪白降为 `Color(2.2, 2.2, 2.2)`（保留轮廓细节），并给每个士兵随机初始攻击相位错开节奏。

## 挑选贴图时要逐张确认

素材包里 240-290 区间混杂着地形、单位、弹道、数字。`tile266`（米色圆盘）、`tile270`（绿色**飞机**，最早被当成"座狼"用）这类名不副实的情况靠文件名完全看不出来。**拷进项目后用 Godot 实际渲染确认一次**，别只看文件管理器的缩略图。
